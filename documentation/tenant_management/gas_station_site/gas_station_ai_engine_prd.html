Purpose: This document elaborates the External AI engine line item from the gas-station implementation record — a separately deployed service responsible for data connectors, forecasting, anomaly detection, and LLM-powered “AI Manager” chat. It reads tenant/station/integration registry from the platform backend and writes back curated daily metrics and recommendations via the existing REST API using a service JWT.

What already exists (this platform): Postgres tables (gas_station_*), Spring Boot CRUD APIs, Next.js admin dashboard (/admin/gas-station), demo seed data, billing. Loop 3 of the feasibility plan is complete — the dashboard works with hand-inserted rows without the engine.

What this PRD covers: The separate adwiise-agent-engine project — architecture, components, training, connectors, LLM agent design, write-back contract, security, phases, and effort.

1. Platform vs engine split

This platform (system of record)

  • Tenant onboarding, subscriptions (Stripe), station CRUD
  • Integration registry (metadata only — no raw POS rows)
  • Daily brief dashboard UI (read metrics + recommendations)
  • Owner actions: Accept / Dismiss / Done + feedback text
  • tenant_settings.gas_ai_engine_* config per tenant

Repos: mosc-temp, event-site-manager, adwiise-agent-service

External AI engine (separate project)

  • POS / fuel / payroll connectors (ingest raw data)
  • Data foundation + feature store (time-series, cleaned history)
  • Forecasting, staffing, pricing, anomaly models
  • LLM layer: explanations + conversational “AI Manager”
  • Overnight batch + on-demand API for chat/refresh

Repo (proposed): adwiise-agent-engine or reuse blueprint at Gas_Station_AI

Contract in one sentence: The platform tells the engine what to connect to; the engine tells the platform what to do today (dollar impact per recommendation) — never the other way around for raw transactional data.

4. Data connectors — process & steps

Connector lifecycle
  1. Discover — Engine calls GET /api/gas-station-integrations?tenantId.equals={id}&isEnabled.equals=true and joins station timezone + capabilities from gas-station-locations.
  2. Resolve secrets — Read credentials_ref from integration row; fetch actual API keys / SFTP passwords from AWS Secrets Manager (never store in platform DB).
  3. Extract — Run provider-specific adapter:
    • API — REST polling (POS end-of-day, fuel controller status)
    • FILE_UPLOAD — Owner or agent drops CSV in S3 inbox; engine parses
    • SFTP — Nightly pull from vendor folder
    • MANUAL — Skip auto-ingest; metrics may be entered in admin until connector live
  4. Normalize — Map to internal schema: transactions, line items, fuel gallons, labor hours, lottery, car wash.
  5. Validate — Row counts, date alignment, station_id match; on failure set integration last_sync_status=FAILED and alert.
  6. Load — Append to raw store; rebuild features for metric_date.
  7. Report — PATCH integration last_sync_at, last_sync_status=SUCCESS via platform API.

5. Model training & learning loops

Important distinction: “Training” here means building and refreshing quantitative models on store history — not fine-tuning the LLM on day one. The LLM starts with strong prompting + RAG; fine-tuning is optional in Phase 3+.

5.1 Cold start (new station, < 30 days data)

  • Use category baselines from anonymized cohort (similar station size, region, capabilities).
  • Recommendations are lower confidence_pct; engine sets conservative estimated_impact_usd.
  • LLM explanations cite “limited history” explicitly.

5.2 Warm model (30–90 days)

  • Per-station time-series forecasts (weekly seasonality, day-of-week).
  • Anomaly thresholds calibrated per station (void rate, cash shortage z-score).
  • Retrain on schedule: weekly batch job reading feature store — not on every nightly inference.

5.3 Continuous improvement from owner feedback

Signal (from platform)Engine use
status = ACCEPTED | COMPLETEDPositive label for recommendation type + category
status = DISMISSED + owner_feedbackDown-rank similar actions; optional LLM summarization of objection themes
Actual vs expected_profit_usd next dayCalibration of impact estimates

5.4 Training pipeline steps (batch, weekly)

1
Extract features for all stations with ≥30 days history.
2
Train per-model artifacts (fuel demand, category sales, labor curve) → versioned in S3 (model_version).
3
Evaluate holdout last 7 days; if MAPE degrades > threshold, keep previous artifact.
4
Promote artifact to “production” pointer used by nightly orchestrator.
5
Log source_model_run_id on every recommendation row for traceability.

6.1 How the LLM connects (no client-side keys)

  1. Owner opens chat in /admin/gas-station (future UI) or clicks “Ask about this recommendation.”
  2. Next.js server action reads tenant_settings.gas_ai_engine_base_url + resolves API key from secrets ref — same pattern as Stripe webhooks using service JWT for backend.
  3. Server POSTs to engine /v1/chat with tenantId, stationId, recommendationId, Clerk userId (audit only).
  4. Engine agent loads context via platform SDK (JWT) — not from browser.
  5. LLM response streamed or returned JSON to server action → UI.
Alignment with cursor rules: Client components must not call the engine or backend directly. All paths go through ApiServerActions.ts on the satellite frontend.

6.2 Example system prompt (MVP explainer)

LLM system prompt — recommendation explainer
You are the AI Manager for a convenience store and fuel retailer. You write clear, brief explanations for store owners. Rules: - Use ONLY facts from the provided JSON context (metrics, model outputs, competitor signals). - State estimated dollar impact only if present in structured fields. - No legal or compliance guarantees; use "consider" not "must". - Max 3 sentences for explanation field. - If confidence is below 70%, mention uncertainty. Output JSON: { "explanation": "..." }

7. Write-back to platform (service JWT)

Write-back contract (v1)

Engine uses dedicated service account credentials (API_JWT_USER / API_JWT_PASS — same pattern as platform proxy). Every request includes:

  • Authorization: Bearer <service JWT>
  • X-Tenant-ID: <tenantId> (required for tenant-scoped APIs)
  • Content-Type: application/json (POST) or application/merge-patch+json (PATCH)

7.1 Endpoints the engine writes

MethodEndpointPurpose
POST/api/gas-station-daily-metricsOne row per station per metric_date (upsert by unique constraint)
POST/api/gas-station-recommendationsN action cards; station_id null for chain-level
PATCH/api/gas-station-integrations/{id}Update last_sync_at, last_sync_status

7.3 Idempotency

  • Nightly run uses source_model_run_id = run_{date}_{tenant}_{version}.
  • Before POST, engine may DELETE or PATCH existing rows for same recommendation_date + source_model_run_id if re-run (agree policy with backend team).
  • Metrics: upsert on (station_id, metric_date) unique key.

  • Optional: webhook from engine when brief ready → trigger email/WhatsApp (Loop 5).

12. Acceptance criteria

Loop 4 complete when:
  1. Overnight job runs for demo_gas_station_001 (or first paying tenant) without manual SQL.
  2. /admin/gas-station daily brief shows engine-produced metrics + ≥3 recommendations including ≥1 with LLM explanation.
  3. Integration rows show last_sync_status=SUCCESS after connector run.
  4. Owner Accept/Dismiss updates platform; next engine run reads new statuses.
  5. All engine→platform calls use service JWT + X-Tenant-ID; no secrets in git.
